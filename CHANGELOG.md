# Changelog

All five npm packages (`@peer2peer/core`, `relay`, `codex-bridge`, `cli` and `ext-ix`) and the Claude Code mod are released together and always carry the same version. [docs/releasing.md](docs/releasing.md) describes how a release is made.

## Unreleased

### Security

- **Your agents' sandboxes now keep them out of `P2P_HOME`, offered by default.** An agent runs as you, so it could read `~/.p2p` (your identity key, the person token, `config.json`'s trust) directly; the CLI's gates and the front ends' guards only stop it running `p2p`. The OS sandbox is the boundary, and it is now set up with your consent instead of by hand:
  - `p2p setup`, in your own terminal, asks about each installed agent on its own: what changes, how to undo it, exactly what it would add to that agent's config, then the question (default Yes); `p2p codex install --write` asks the same for Codex. A no is remembered per agent (`"sandboxDeclined": ["claude"]` in config.json); `p2p setup --sandbox` and `p2p sandbox enable [--claude] [--codex] [--yes] [--codex-base read-only|workspace]` ask again (`--yes` is refused on Windows), and `p2p sandbox` shows where things stand.
  - **Claude Code** (`~/.claude/settings.json`, or `$CLAUDE_CONFIG_DIR`): `sandbox.enabled: true`, `sandbox.autoAllowBashIfSandboxed: false` (your permission prompts stay; releases before v2.1.324 defaulted it to true; not written if you set it), `sandbox.allowUnsandboxedCommands: false`, `P2P_HOME` in `sandbox.filesystem.denyRead` and `denyWrite` (enforced by Seatbelt or bubblewrap on Bash commands and everything they start), and `Read(…/**)`/`Edit(…/**)` deny rules for Claude's own file tools. Turning the sandbox on also confines those commands' writes to the project and their network to hosts you allow, and a command it blocks fails.
  - **Codex** (`config.toml`): a permissions profile, `peer2peer`, that denies `P2P_HOME`, made the default, and never broader than before: `sandbox_mode`, when set, alone decides what it extends (`:read-only` or `:workspace`; the line is commented out, since Codex ignores profiles while it is set), else a built-in `default_permissions`; a config that sets no sandbox gets `:read-only` (`--codex-base workspace` chooses workspace writes, in untrusted folders too). `[sandbox_workspace_write]`'s `writable_roots` and `network_access` are carried over only under `sandbox_mode = "workspace-write"`. A profile of your own that is already the default gets the deny line instead. Checked with `codex sandbox` (codex-cli 0.156.1, macOS): a read and a write under the denied folder fail.
  - Each file is backed up first (`<file>.p2p-backup-<time>`, 0600, beside the path as named, not a symbolic link's target), everything else in it is kept (other keys and indentation in JSON; every other line and comment in TOML), nothing is written if it changed after it was shown, and a second run changes nothing. What can't be edited safely (including a `P2P_HOME` with rule characters, or one that is the home folder or above it) is left alone, with the reason printed.
  - Only you change it, in your own terminal: refused inside an agent's session, when the process tree can't be read, and from a front end even with its token. The Claude Code mod never edits your settings; it tells you once, in a toast, to run `p2p sandbox enable` (an agent's shell without the token can't use the notice up).
  - `p2p doctor` (`/peers doctor`) has a line for each installed agent: whether its sandbox denies `P2P_HOME`, what is missing, and the fix. It also reads the session's project settings (`.claude/settings.json` and `settings.local.json` turning the sandbox off or opening `P2P_HOME`; a project `.codex/config.toml` that picks its own sandbox makes Codex's line ?), and on Linux checks for bubblewrap and socat.
  - The front ends keep working: what a mod starts, hooks and MCP servers run outside the agents' sandboxes, so the mod's and the bridge's own `p2p` runs read `P2P_HOME` as before. The agent's own shell can't run `p2p` any more (not even a read); it uses the front end's tools. What the sandbox doesn't cover (excluded commands, approved escalations, a project's own settings, native Windows) is in [docs/security/threat-model.md](docs/security/threat-model.md#the-hard-barrier-sandbox-your-agents).
- **A key holder's head stored first no longer keeps a device trusted that your later version revoked (#92).** If a peer stored a version signed with your identity key that kept device D (v8', unanchored), and your own revoking v4 reached it later while the relays held your history only from v2 or v3 up, nothing connected the two: the refresh stayed incomplete but the view still trusted D, and once v4 expired the refresh completed with D still trusted.
  - A current version a relay serves below the held unanchored head is now kept as another root, with the ancestry the refresh fetched placed under it, when that ancestry shows it revoked a device every held tip lists. A revoked device never returns and a merge never adds one, so no held tip can descend from it: the view shows the fork and trusts only what both list, for good. An older honest version still served by a stale relay never revokes what the head lists, so it is never placed this way.
  - When even that version's parent is gone, a version the refresh held back for now narrows the view while it is current, as a pending head does above the head (never for your own identity, and cleared by the next complete refresh a majority of the relays answered).
  - From #87's review: a key holder filling the side-root slots with same-ver forks no longer keeps your same-ver tip out, since a tip that leaves out a device or key holder every tip lists is placed past the cap (it only narrows). A version dropped because its link to its parent is broken is off valid history, and so is everything placed on it: dropping them no longer gets what they left out denied for good.
- **Rotating from a forked identity: low follow-ups from #89's review (#91).**
  - When your identity is forked by a version that leaves this device out and provenance picks one branch as yours among others that still list this device, the rotation warns and its plan lists the other branches (tip, ver, publishers, relays), with how to choose another (`--cancel`, then `--plan --branch <hash>`). A stolen key holder's branch can no longer be picked silently.
  - A plan that isn't accepted yet is reused, so `--plan --branch` or `--resume --branch` naming another branch than the plan's own is now refused, telling you to drop the plan first (`--cancel`), instead of being ignored.
  - If someone holding your identity key publishes a rotation while yours is under way from your own branch, `--resume` now says so and points to `p2p identity rotate --resume --contest` (your rotation goes on as a competing one, so your friends see a conflict and apply neither), instead of telling you to run `--resume` again; the error names the device that signed that rotation. A plan not yet accepted is refused there (drop it with `--cancel`, then `--contest`, whose plan drops the device that signed the rotation and every other key holder); past acceptance, those devices are dropped if no link code went out yet, and otherwise named so you can revoke them on the new identity. In this fork case the competing final version reaches no relay: your friends see the conflict from your new identity's invites. One `identity rotate` run per home at a time: a second run while one is in progress is refused (`rotation_in_progress`).
  - The branch summaries (in the plan and in the `branch_ambiguous` error) show only canonical relay URLs and device ids: core already keeps anything else out of a verified version, and they are checked again before they are printed.
- **A relay is set aside for a rotation only for your own version (#92 follow-up).** A relay a refresh of your identity was held back for (it serves a head that leaves out a current version, and none of those versions) is now set aside before a rotation only when a version it left out is your own current tip: a tip of the history this device holds (never an old version a relay replays) that your devices published (the publish log), or, when the head it was held back for leaves this device out as a key holder, that a device a version in the publish log lists published (never against a head that still lists this device: a version a device you revoked since signed can't get the relay serving your revocation set aside). Otherwise rotation refuses as before and names the relay, which you can remove (`p2p relays remove`): a relay replaying an old version can no longer get an honest relay set aside. Core reports the left-out versions and the head held back for (`heldBackFor`, `heldBackHead`, next to `heldBackBy`).
- **Rotation: low follow-ups from #98's review (#99).**
  - Your own published tip no longer gets the relays serving a head set aside when that head revoked a device the tip lists (and still lists this device). That head may be your own revocation, made on another device while this one was offline longer than the relays keep the history between them: a hostile relay still serving the old version can no longer make the rotation plan from its stale device list. A thief's head that adds a device and drops none of yours, or that leaves this device out as a key holder, is handled as before. Core's `heldBackHead` now carries the head's `devices`; without them (an older core) the tip doesn't count.
  - The rotation lock (`<home>/rotation.lock`) records the process's start time and a random run id next to its pid, so a pid a later process reuses no longer keeps rotation refused: the lock is taken over. When the start time can't be told the lock still counts as held, and the error names the lock file and says to delete it if nothing is rotating.
  - Taking over a stale lock is exclusive: two runs that find the same stale lock leave exactly one owner (the other is refused with `rotation_in_progress`), and a run only ever removes its own lock.
  - `p2p identity rotate --plan`, `--cancel` and `--resend` take the lock too, so a `--plan --exclude <did>` racing a `--resume --yes` run can no longer lose the exclusion.

### Fixes

- **The Codex bridge reads newer Codex rollouts.** Codex 0.169.0 stopped writing `sandbox_policy` into a session's turn context and writes only `permission_profile`, so on those versions the bridge saw no sandbox at all: the mode stayed unknown, every message from another person was held and every release refused. It now reads `permission_profile` too: no write grants is `read-only` (`:read-only`, or a profile extending it with deny entries, like the `peer2peer` one `p2p sandbox enable --codex` writes), any write grant is `workspace-write` with those folders as the writable roots, a disabled sandbox or unrestricted file system is `danger-full-access`. Where a turn context has both fields (Codex 0.130 to 0.168), `sandbox_policy` still decides and the profile can only widen it; a profile whose writable folders can't be read makes them unknown even then. A turn context with neither, either one present but unreadable, or a shape it doesn't recognise still counts as unknown: held, releases refused.
- **A turn context too long to read no longer leaves the previous mode in force.** The bridge skips rollout lines over 1 MiB; when a skipped line is a turn context (told from its first bytes), the rollout is no longer trusted: held, releases refused.

## 0.1.3

A security release. Nothing changes on the wire: 0.1.3 clients interoperate in both directions with 0.1.2 and 0.1.1, which the cross-version matrix ([docs/compatibility.md](docs/compatibility.md)) checks against the previous two releases, as committed at their tags and as npm installs them.

### Upgrade

- Install with the one-line installers once they're pinned to 0.1.3, or `npm i -g @peer2peer/cli@0.1.3 @peer2peer/ext-ix@0.1.3`. The Claude Code mod ships matching copies of both. Each package depends on exactly `0.1.3` of the others.
- **The person token changes format on first run.** On a home with an identity it is now derived from the device key (see Security). The Claude Code mod gets one `person_token_stale`, reads `<P2P_HOME>/cli/person.key` again and retries, as it already does; the Codex bridge's first command after the upgrade fails once with `person_token_stale` and its next one picks up the new token. Scripts that pass `P2P_PERSON_TOKEN` should read that file on every run.
- **More commands ask for you.** Commands that touch your identity key or document, or narrow who reaches you, now need the front end's token or your `yes` on the terminal, and are refused inside an agent's session (list under Security). At a plain terminal, `identity rotate` and `ix import` ask that `yes` before their own question.
- `p2p relays remove` takes several relays at once.

### Security

- **Commands that touch your identity key or document, or narrow who reaches you, are now the person's only, checked by the CLI itself.** The agent guards in the Claude Code mod and the Codex bridge read command lines, so an agent could get past them by building the CLI's name at run time or by running a script it wrote, and these commands had no check of their own: an agent could print your 24-word backup phrase (`backup show`), or rotate your identity with `--yes --backup-file <path>` and read the new phrase. They now take the same gate as the widening commands: your front end's token (the mod's typed `/peers`, the Codex bridge), or your `yes` typed on your own terminal, and never from inside an agent's session. The CLI decides from the command it parsed and its agent detection (environment and process ancestry), not from the command line's words. Covered:
  - `backup show`, `backup restore`, and `setup --print-backup|--backup-file` on a home that already holds an identity (`backup restore` runs only on a fresh home and needs the phrase itself, so outside an agent's session the phrase is the proof and nothing more is asked; inside one it is refused);
  - `identity rotate`, except a bare `--plan` (it makes or shows the plan and reveals nothing; accepting it with `--resume`, `--cancel`, `--backup-file`, `--exclude`/`--keep`/`--invite`, `--keep-keyholders`, `--contest`, `--resend` and `--yes` are gated), `identity republish`, `identity dispute`;
  - `devices revoke`, `relays add`, `relays remove`, `profile set`, `proof add`;
  - `trust remove`, `invites revoke`, `remove`, `unfriend`, `block`, `petname`, `circle propose`, `circle transfer`, `circle leave`, `circle hold <cid> on|off`, `held decline`, `extensions disable`, `receipts on|off`, `ix import`, `ix resolve`, `ix config <setting>`.
  Reads stay open (`receipts`, `circle hold <cid>`, `ix config`). `p2p watch`'s automatic renewal of your document and certificates is maintenance, not a command, and keeps working inside an agent's session. Scripts and CI that run these as you pass the person token, as for the widening commands.
- **Agent detection reads the process tree with the system's own tools and fails closed.** It reads `/proc` on Linux and runs `ps` by absolute path (`/bin/ps`, `/usr/bin/ps`) elsewhere, never through `PATH`, so a `ps` put first on `PATH` can't answer "no agent". The walk ends at the root or at another user's process (also one `/proc` hides with `hidepid`, so a person over ssh isn't refused). When the tree can't be read (a process of yours, a `ps` that fails or times out: run the command again), or the CLI runs in a nested PID namespace (a container, `bwrap --unshare-pid`, where an agent outside can't be seen), the person-only and widening gates refuse without the token, as inside an agent's session. The person's token still works there: pass it inside a container. Windows has no process-tree check (it fails open there).
- **The person token is derived from the device key on a home with an identity.** It is an HMAC under the device's signing key over a per-home salt (`cli/person.salt`, replaced whenever an identity is created or restored), recomputed on every check, so a `person.key` written by anything else never verifies. The CLI also refuses the token, and never writes one, in a home whose `cli` folder, keys or self documents, token, salt or `v3` store is a symbolic link (or whose keys or self document has a second hard link): before, a home made of links to your files with a `person.key` of the agent's choosing counted as you. The token is checked again after the command finishes an interrupted rotation follow (which no longer moves a symbolic link into the home), and against the keys the command loads, so a home whose files change while the command runs (or that had no identity when the token was checked) never lends the token to other keys. A home whose `cli` folder is a link (a dotfile manager's) can't use the token, and the refusal says so. A front end's old token is refused once after the upgrade (`person_token_stale`); the mod and the Codex bridge read `person.key` again by themselves.
- **`p2p invites` cuts its live codes inside an agent's session.** Without the person's token, open codes (and taken ones nobody joined yet) are shown as their first four characters, in the JSON too (`redacted: true`), as redeemed ones already were. The statuses stay readable.
- **What this is not:** a boundary against an agent that runs as you and means to get past it. A process it starts outside its own process tree that fakes a terminal can answer the terminal `yes`, and a process running as you can read your key files directly. Sandbox your agents, denying them read and write access to `P2P_HOME` ([docs/security/threat-model.md](docs/security/threat-model.md)).
- **Your edits no longer build on an old version of your identity when your up-to-date relay doesn't answer ([#78](https://github.com/ix-infrastructure/Peer2Peer/issues/78)).** Before publishing, your device checks your current version with the relays you list, and skips the ones that don't answer. If the relay holding your newest version timed out while a relay behind it answered, an edit could be published on the older version, even though your device already held the newer one from an earlier, cut-short check. That forked your own identity. Now:
  - your device keeps, next to each newer version it couldn't connect yet, which relays sent it (stored locally only);
  - an edit refuses while one of those relays doesn't answer and the relays that did answer only confirm an older version. The error names the relay: try again when it answers, or remove it with `p2p relays remove <url>` if it's gone for good or no device of yours published that version;
  - a relay can hold your edits up only while it stays silent. Once it answers, or is removed (removing it always goes ahead; relays that hold each other up are removed together), or is found serving versions that don't connect to your history, it no longer does. Newer versions stored by earlier releases, with no record of who sent them, never hold an edit up;
  - `p2p relays remove` now takes several relays (`p2p relays remove <url> <url>`), removed in one new version: two silent relays that each sent a different newer version would otherwise each hold up removing the other;
  - this is never silent when it holds up renewing your identity document: a key holder's background renewal warns on every run, and once renewal is due the Claude Code mod's status line shows an alert (raised again each day left until it expires). `p2p doctor` lists the newer versions your device holds, which relays sent them, and which of those don't answer, with the `p2p relays remove` fix.
- **A relay that can't be reached no longer counts as having answered "nothing" when your device refreshes anyone's identity ([#78](https://github.com/ix-infrastructure/Peer2Peer/issues/78)).** Before, an unreachable relay counted toward the majority of an identity's relays that has to answer before a refresh counts as fresh and clears what the newest versions revoke ahead of time. Side effects to know about:
  - with one of two listed relays dead for good, refreshes of that identity never reach a majority: it isn't marked fresh, and pending newer versions of it are only dropped once the held version reaches them or they expire. Remove a relay that is gone for good (`p2p relays remove <url>`, or ask the friend to);
  - a relay serving forged versions of your identity is only named (and set aside by `p2p identity rotate`) when every other relay answered. If one of your relays is down, remove the forging relay first, then rotate.
- **The Codex bridge's agent guard refuses every `p2p` verb the Claude Code mod's refuses.** Its verb lists had fallen behind the mod's, so a Codex agent's shell could run `identity rotate`, `identity follow`, `identity dispute`, `trust add`, `trust remove`, `extensions enable`, `extensions disable`, `invites revoke`, `circle hold`, `unblock`, `tui`, `status`, `ix import`, `ix resolve`, `ix note`, `ix subgraph`, `ix impact`, `ix config` and `ix footprint --publish` without the guard refusing them. The CLI itself refuses some of these inside an agent's session (`trust add`, `identity follow`, `extensions enable` and `unblock` need the person; `status`, `ix note|subgraph|impact` and a footprint publish need the session's front end; `tui` refuses an agent), so for those the bridge's guard was a second check. The others (`identity rotate --yes`, `identity dispute`, `trust remove`, `extensions disable`, `invites revoke`, `circle hold`, `ix import`, `ix resolve`, `ix config`) had no other check against the agent. Both guards now hold the same lists, word for word; the mod also refuses `release` anywhere after the CLI's name, as the bridge already did.
  - The lists are pinned in `mods/claude/peer2peer/tests/guard-verbs.vectors.ts`, which both test suites read: each guard's lists must equal it, and every verb has command lines (flags before, between and after its words, inside `bash -c` and `sh -c`, behind `nohup`, `nice`, `timeout`, `eval`, `env -S` and `npx`) that both must refuse with the same verb. A verb added to one guard and not the other fails both suites.
- **The owner can rotate after someone holding the identity key forks it with a version that leaves the owner's devices out.** Such a version connects to the owner's history, so the owner's view forks, the owner's devices fall out of the allowlist, and the relays refuse them. Before, `p2p identity rotate` refused with `device_revoked`, and so did the final version's publish, which merged the fork first. A failed edit also kept that merge, which hid the owner's own branch afterwards; rotation now drops such a merge when no relay serves it. Now rotation runs from the device's own branch: a tip that still lists it as a key holder, chosen by who published the versions on it, never by version number. When that can't tell (someone else's branch also lists the device and was published by one of your devices), the command refuses with `branch_ambiguous`, lists the branches, and you choose one with `--branch <hash>`. The plan lists that branch's devices, and friends this device made are invited. The old identity's final version follows a merge of the tips that lists nobody, with the relays of the newest version this device published plus its configured ones. A relay that refuses the device gets it over a restricted connection with a throwaway device certificate. Friends follow it as usual. A device that no tip lists still can't rotate. The owner's other devices can't be reached through the relays then, so they re-link by hand. ([#75](https://github.com/ix-infrastructure/Peer2Peer/issues/75))
- **A key thief's higher branch can no longer drop the owner's revoking version at first contact ([#79](https://github.com/ix-infrastructure/Peer2Peer/issues/79)).** When a refresh over no (or only unanchored) history got two tips that don't connect, say the owner's version revoking a device and a higher version a thief signed with the identity key keeping it, the owner's version was placed first and then replaced by the thief's (the rule that lets a newer version replace unanchored history). Its parent wasn't held, so what it revoked was lost and the revoked device stayed trusted until a later refresh. Now a refresh never replaces held history while placing versions: the higher version waits as a gap, the walk also asks for the parent of each unanchored root a replacement would drop, and the replacement (or jump) happens only at the end, carrying what every held branch revoked. A version a held unanchored root names as its parent is placed below it even when version 1 is out of reach (relays keep old versions only for a while), so the root's revocation is known and a branch forking off below it connects. With both chains served, the view shows the fork; with the thief's relay withholding its chain, the owner's version is walked down and its revocation stays on the denylist. A held version whose link to that parent breaks the chain rules, or that lists again a device revoked below it, is dropped instead (as it would have been refused in the other order), never the parent. When the walk can't connect them, a current version the result would leave out (a held tip or root, stored earlier or served now, or a tip a relay served that didn't connect) doesn't give way to a head that lists a device or key holder it doesn't: the refresh ends incomplete, nothing is replaced, and only what both list is trusted, until the chain connects them or that version expires (30 days at most). This applies only when that version has at least as much relay support as the head, or when the head lacks a majority of the listed relays, so one relay replaying an old version can't hold back a head most listed relays serve. On your own identity, an edit held back this way refuses and names the relays that sent the newer version (someone else may hold your identity key), and `p2p identity rotate` leaves those relays out, as it does relays serving versions that don't connect, so a key holder can't block your rotation. Two unconnected tips at the same version are kept side by side, as a fork. A version placed before its parent arrives is checked against that parent when it does, so a version with a broken link can no longer be stored, and a store already holding one loads without it instead of failing on every load. What a dropped version (and any dropped with it) revoked stays revoked, so dropping only ever narrows. A newer version that lists nothing more still replaces unanchored history when the relays can't connect it, without a history gap, as before.
- **Replaying a long history's pruned old versions no longer keeps its refreshes incomplete ([#81](https://github.com/ix-infrastructure/Peer2Peer/issues/81)).** On a history longer than 1024 versions, one relay serving a pruned old version (with its ancestry) left a gap whose missing parent was the pruned version 1, which is never stored again. Every refresh then ended incomplete: freshness was never recorded and approvals were refused. Such a gap is now settled and never walked. A second version 1 below the pruned range is still a fork.

## 0.1.2

Nothing changes on the wire. 0.1.2 clients interoperate in both directions with 0.1.1 and 0.1.0. The cross-version matrix ([docs/compatibility.md](docs/compatibility.md)) checks this against the previous two releases, as committed at their tags and as npm installs them.

### Upgrade

- **Install it with the one-line installers** (new in this release): `curl -fsSL https://ix-infra.com/p2p/install.sh | sh` on macOS and Linux, or `irm https://ix-infra.com/p2p/install.ps1 | iex` on Windows. Or `npm i -g @peer2peer/cli@0.1.2 @peer2peer/ext-ix@0.1.2`. The Claude Code mod already ships matching copies of both.
- **Someone who already uses Peer2Peer on another device should link a new device, not start a new identity:** run `p2p setup` and answer `l`, or `p2p link start` on the device you already use and `p2p link join <code>` on the new one.
- Each package depends on exactly `0.1.2` of the others.

### Behaviour changes

- **The agent guards refuse more command lines they can't read by their words, and the Claude Code mod and the Codex bridge now agree on them.** A shell command from the agent that names p2p is refused, not emulated, when:
  - GNU `parallel` (or `sem`, `parset`, `rush`, `xjobs`), or `xargs` (`gxargs`, `busybox xargs`), runs in a simple command that names p2p or expands something (`parallel p2p ::: invite`, `echo invite | xargs p2p`, `setsid parallel p2p …`). As the command word, they're also refused when they take their arguments from stdin or a file on a line that names p2p (`echo 'p2p invite' | parallel`), or when xargs runs a shell (`… | xargs -I{} sh -c '{}'`). The guards see the command word behind wrappers and their option values (`sudo -u x`, `timeout -s KILL 5`, `flock <file>`, `coproc`, `setsid`, `chrt`, `taskset`, `ionice`, `caffeinate`, `unshare`). The bridge didn't check `xargs` before.
  - It defines an alias in a simple command that names p2p or expands something (`alias q='p2p send --to'; q …`), uses `hash -p`, assigns to zsh's `functions[…]`/`aliases[…]` or bash's `BASH_ALIASES`/`BASH_CMDS`, sets `PROMPT_COMMAND` to something naming p2p, or defines any shell function. Functions are caught in bash's and zsh's forms: `f() { … }`, `f() ( … )`, with a comment or newlines before the body, zsh's `f() cmd`, and zsh's anonymous `() { … }`.
  - A command word is built at run time (`p=parallel; $p p2p …`, `$(which parallel) …`), `eval` runs text built at run time that names p2p, or a script is sourced from a process substitution or a path that names p2p. The bridge didn't check run-time command words before.
  - It nests shells or `eval` deeper than the guards read, and still names p2p there, however the words are quoted (`e''val`, `ev\al`). Before, the guards stopped reading at that depth and let the command through.
  - It's too complex to check in a bounded amount of work. The verb check reads each nested command line once per level and stops at a fixed budget (64 passes over the longest command checked), so the guard always answers well within the hook's timeout. A command that names p2p and goes past that budget is refused. Before, a command padded with runner words (`echo trap trap … ; p2p send …`) could take the Codex bridge's guard longer than the hook's timeout.
- **Strings and substitutions are read as the commands they run, by both guards.** Backtick substitutions are read again, like `$(…)` (``echo `parallel p2p ::: invite` ``). So are the strings that `trap`, `su -c`, `complete -C`, `ssh host` and `watch` run (`trap 'p2p invite' EXIT`). A shell's `-c` script is read together with the positional arguments after it, which it can run (`bash -c '"$@"' x eval 'p2p invite'`), and so are the arguments of a script file. A line read again this way is never taken for a text command's arguments, because its quoting is gone.
- **The Claude Code mod finds the CLI anywhere in a simple command, as the Codex bridge does,** unless the command is a text command (`echo`, `grep`, `git`, …). That covers the CLI behind wrappers the mod didn't know (`setsid p2p invite`, `watch -n1 p2p invite`, `find -exec p2p invite \;`, `fd -x p2p invite`, `ssh host p2p invite`), including behind a shell's `-c` there. The mod's check for `gh alias`/`gh extension` now matches those subcommands as words, so a `gh pr create --body` that mentions them passes.
- **`env -S` is read the same way by both guards.** The Codex bridge now unwraps `env -S '<command line>'` (and `-S<line>`, bundled `-vS`, `--split-string[=]`) as the Claude Code mod does, so a `p2p send` inside it is refused by both. Both read `-S` only among env's own options, before its command.
- **What still passes:**
  - Quoted text isn't read as a function definition (`p2p send … 'f() { x }'`), and neither is the body of a quoted heredoc written by a text command (`cat > f <<'EOF'`).
  - A text command's arguments aren't read again as a script (`git commit -m 'guard parallel p2p runs'`).
  - `parallel`, `alias` and `xargs` pass in a simple command that doesn't name p2p and takes its arguments inline (`p2p ls; parallel echo ::: a b`, `echo p2p; alias ll='ls -l'`, `… | xargs -n1 echo`).
- **Not covered, as before:** like every guard here, this is defence in depth on top of the agent's permission prompt, not a boundary. These aren't read:
  - a symlink or a script file that gives the CLI another name (`ln -s "$(command -v p2p)" /tmp/q; /tmp/q invite`);
  - commands queued for later from stdin or a file (`at`, `batch`), make recipes (`make -f <(…)`, `--eval`), and a script that xargs (or a runner) reads from a file and hands to a shell on a line that doesn't name p2p (`xargs -a cmds.txt -I{} sh -c '{}'`);
  - a carriage return inside the `--to` word of a `p2p send` (the send's target then can't resolve).
- **Identity histories longer than 1024 versions now count as anchored after old versions are pruned, so automatic gap jumps are off for them.** Before, pruning a long history's version 1 made it count as unanchored again, so a newer version that didn't connect replaced it, or the history was jumped over without asking. Now a friend with such a long history whose relays dropped the versions in between needs an explicit jump (`jumpIdentity`, with the "history gap" warning) instead of an automatic one. A replay of their pruned version 1 is ignored as known history. ([#74](https://github.com/ix-infrastructure/Peer2Peer/issues/74))
- **Scripts and CI: a `P2P_PERSON_TOKEN` that doesn't match `<P2P_HOME>/cli/person.key` now fails the command** with the error `person_token_stale`, and nothing is done. Before, the command ran as if no token were given (not as the person). The file is replaced whenever an identity is created or restored on the home (see Security below), so read it again on every run rather than keeping the value from before `setup` or `join`.
- **`p2p setup` asks how you're joining before it makes any key.** At your terminal, with no identity on this device, setup first asks: `[l]` I already use Peer2Peer on another device, `[i]` I have an invite link or code, or `[n]` start a new identity.
  - `l` links this device to the identity you already have (the same as `p2p link join`, inline): run `p2p link start` on the other device (or `/peers link start` in Claude Code), then type the code it shows. Before, setup could only make a new identity, so someone who already had one ended up with a second, separate identity.
  - `i` redeems the invite (the same as `p2p join`, inline): the new identity uses the relay in the code, so no relay is asked for.
  - `n` asks for your group's relay URL when none is given (`--relay`, `P2P_DEFAULT_RELAYS` or `defaultRelays` in config.json). Only `wss://` relay URLs are taken (a bare host means `wss://`). There is no default relay: bring your own.
  - The backup question (file, print or skip) now comes only after the identity exists, never before its key is made: a setup that stopped with `no_relays` used to ask it first.
  - `l` and `i` keep their person-only gates (the front end's token, or your `yes` on the terminal). Agents are never asked: setup stays refused in the Claude Code mod and the Codex bridge.
  - With `--json`, `CI` set, without a terminal or inside an agent's session, setup behaves as before. With no relay configured, its `no_relays` error now names all three ways in: `p2p link start` and `link join <code>`, `join <invite>`, or `--relay wss://…` (`p2p.cmd` on Windows).
  - The installers' hand-off says that someone who already uses Peer2Peer on another device should link this device in setup.
  - Setup's link path says to type only a code shown on your own other device. An invite pasted there is joined as an invite, with its own confirmation. A `p2p-link:` code pasted at the invite question is refused, because a link code from anyone else makes this device theirs.
  - Setup has `--allow-private-relay` for an invite or link code whose relay is on a private address, as `p2p join` has.
  - The no-backup warning now comes on every `p2p setup` while this device is the only key holder and the phrase was never shown, not only right after the identity was created.
- **`p2p link join` shows which identity this device would become and keeps nothing until you say it is yours.** After the other device answers, the new device shows the identity's address and fingerprint and asks, on your own terminal, "Is this your identity?". A no keeps nothing on this device. Before, a link code from someone else silently made the device theirs. Scripts pass `--expect-fingerprint <fingerprint>` instead. The same applies to setup's link path.
- **A link code's relay gets the same private-address rule as an invite code's.** A link code whose relay is on a loopback, link-local or private address is refused before anything connects there, unless that relay is already yours (`P2P_DEFAULT_RELAYS` or `defaultRelays` in config.json) or you pass `--allow-private-relay` (or set `P2P_ALLOW_PRIVATE_RELAY=1`).
- **On a device with no identity yet, the person token no longer stands in for you on `p2p link join` or on setup's link and invite paths.** Your `yes` on the terminal is asked instead. A `person.key` on a fresh home may have been put there by anything that can write the folder, and honouring it would have let that make the device someone else's without you. No front end runs these commands: setup and link are refused in the Claude Code mod and the Codex bridge. A typed `/peers join` on a fresh install keeps working as before.
- **Ix is optional and recommended; Peer2Peer never installs it for you.**
  - `p2p setup`, run by you at a terminal, explains in a few lines what Ix adds (overlap with peers' sessions, a change's blast radius, local graph memory; all local) when it isn't installed, and asks `Install Ix? [y/N]`. The default is No. A yes prints the install command for your platform, for you to run in your own terminal, then `p2p setup --ix` turns on the Ix extension. Peer2Peer never runs an installer.
  - A no is remembered (`"ixDeclined": true` in config.json) and setup doesn't ask again. `p2p setup --ix` asks again.
  - Setup never offers Ix with `--json`, with `CI` set, without a terminal, or inside an agent's session. (Turning on the Ix extension when Ix is already installed still asks for your `yes` on the terminal, as before, even with `--json`.) `p2p setup --json` reports `ix.installed`, `ix.recommended` and `ix.install` (the command to run) instead. `p2p extensions --json` reports the same under `ix`.
  - The Claude Code mod (beside the first prompt you type) and the Codex bridge (at session start) tell the agent once per session, when Ix isn't installed and you haven't said no, that Ix is optional, that it may suggest Ix to you once, and that it must never install Ix itself.
  - In Claude Code, an agent's shell command that installs Ix (the Ix install scripts, its Homebrew tap or formula, or a global npm install of the Ix CLI package) goes to your permission prompt, even in a mode or under rules that would allow it. Where nobody can be asked, it is refused. A URL counts only in a segment that fetches it (curl, wget, irm, iwr, Invoke-WebRequest, Invoke-RestMethod, or .NET's WebClient DownloadString/DownloadFile), on any port, so reading or searching for it doesn't ask. npm and brew are found anywhere in a command (behind sudo, nice, arch, xargs, stdbuf and the like), and line continuations (`\` or PowerShell's backtick at a line's end) are joined first. It is a loose text match that errs toward asking: quotes and comments aren't read, so mentioning an Ix install command anywhere in a shell command asks, even inside a commit message or an `echo`. Other commands are unaffected.
  - Enabling the Ix extension is still yours alone, as before: the front end's token or your `yes` on the terminal, never from inside an agent's session. `p2p doctor` says Ix is optional and shows the install command.

### Security

- **A relay replaying a friend's old public versions can no longer fork their identity at your end.** Most stored views of a friend's identity are unanchored: they start from the head you first saw, with no version 1 behind it. Before, any single relay could send that friend's genuine version 1 (or an old version, whose gap was then walked down to version 1), and it was kept as a second branch: the view went `forked`, only the devices both branches list were trusted (often none, once the first device was retired), the fork survived refreshes from honest relays, and the history counted as anchored, which turned off replacement by a newer version and automatic gap jumps. No identity key was needed. Now, while the held history has never been anchored at version 1, a branch starting at version 1 that doesn't connect to the head's history and lies wholly below its lowest version is old history, not a fork. It is kept, and counts fully once the versions in between connect it. Until then it isn't a tip, isn't intersected with the head, and doesn't make the history anchored, but what it signed still applies: the devices revoked along it stay untrusted (also after the history is replaced or jumped over), and a rotation it carries is shown. A second version 1 is still a fork once the history is anchored at version 1, and stays one after old versions are pruned. On a long history whose version 1 was pruned, the history stays anchored (not replaceable by a newer version that doesn't chain, and not jumped over automatically), and a replay of that pruned version 1 is history, not a fork. Two tips whose common history has to be walked down to version 1 are still a fork. Stores already affected heal when next read, with nothing to do. ([#74](https://github.com/ix-infrastructure/Peer2Peer/issues/74))
- **No polynomial-time regexes on peer, relay or agent text.** The open CodeQL `js/polynomial-redos`, `js/identity-replacement` and `js/incomplete-html-attribute-sanitization` alerts are fixed with linear scans (address and `[ref]` parsing, label, path and quote trims, URL userinfo redaction) that give the same results. The relay's allow file and the Codex bridge's config.toml check now end a `#` comment at any line ending (CRLF, CR, U+2028, U+2029), so a comment in a CRLF file no longer leaves its words behind as ids.
- **A person token planted before an identity exists no longer works once it does ([#70](https://github.com/ix-infrastructure/Peer2Peer/issues/70)).** `p2p` replaces `<P2P_HOME>/cli/person.key` with a fresh token whenever an identity is first created or restored on a home: `init`, `setup`, `join` on a fresh home, `link join`, `backup restore` and identity rotation. A key put there by something that could write the folder before setup kept standing in for the person afterwards, letting it skip the widening gate on every later command. The command that creates the identity still runs with the token it started with, so a typed `/peers join` on a fresh install works as before.
  - A `P2P_PERSON_TOKEN` that isn't the home's is now refused before the command does anything, with the error `person_token_stale`, instead of being quietly treated as "not the person". The Claude Code mod reads `person.key` again and runs the command once more. The Codex bridge now reads it for every run (it used to read it once, when the session started). Scripts that pass the token should read the file on every run too. The token is replaced before any key is written, so if it can't be replaced, no identity is made. A home counts as holding an identity only when both its keys and self documents exist.
- **Identity refreshes: what the newest version revokes applies even when a refresh is cut short.** On slow hardware, a refresh far behind can end incomplete after committing an older version that still lists a device the newest version removed. That device is no longer trusted meanwhile. The verified versions above the stored head are kept as pending heads, and while any is still above it, only the devices and key holders every one of them lists are trusted. This narrowing is temporary and never goes on the permanent denylist:
  - the next complete refresh answered by most of the relays the identity lists clears it (a stale answer from a minority, or from relays named only by an unverified link, doesn't);
  - a pending head issued in the future or past its expiry is ignored;
  - it never applies to your own identity on your own devices: a version only your identity key signed (for example a thief's) can't stop you editing, publishing or rotating your identity, or your devices accepting each other's syncs. ([#35](https://github.com/ix-infrastructure/Peer2Peer/issues/35))
- **You can always remove a relay that serves forged versions of your identity, and rotate.** Someone holding your identity key and one of your relays can serve versions signed with that key that don't connect to your history. Your device's check before publishing then couldn't confirm your current version, and refused every edit, including removing that relay and rotating (the only remedies). Now:
  - `p2p relays remove <url>` checks your current version with the relays you keep, and goes ahead when they confirm it;
  - `p2p identity rotate` leaves out a relay that sent versions whose history no relay holds (every relay was asked), when your other relays confirm your current version and no relay kept serves a newer one; otherwise it refuses, and removing the relay first still works;
  - any other edit still refuses while such a relay is listed, and names it, with what to do;
  - you are warned that someone else may hold your identity key only for such a relay.

  What you publish is always the next version on the version your other relays confirm, so a relay can't make you publish below it or beside it. ([#67](https://github.com/ix-infrastructure/Peer2Peer/issues/67))
- **A genuine history gap is reported as one.** A refresh is cut short by a gap only when a relay held the missing version but it wasn't checked in time. A relay answering with junk no longer turns a real gap (pruned history) into "cut short, try again" on every refresh. An honest relay that runs out of time or allowance still counts as holding the version, so no relay can turn another's slowness into a broken chain. ([#35](https://github.com/ix-infrastructure/Peer2Peer/issues/35))

### Fixes

- **A contact far behind catches up.** A device more than about 256 versions behind someone's identity (per relay holding it) never caught up: every refresh walked back from the newest version, ran out of allowance before reaching what it held, and ended "cut short" without progress. Where a refresh's walk stops is now kept on the device, and the next refresh goes on from there, so each refresh makes progress. Also: when the relays have nothing for one gap, the walk tries the next one instead of stopping, and a relay's junk sorted ahead of a genuine missing version can no longer keep a gap "cut short" on slow hardware. ([#67](https://github.com/ix-infrastructure/Peer2Peer/issues/67))

### Fixes (known issues from the pre-release review, [#3](https://github.com/ix-infrastructure/Peer2Peer/issues/3))

- **An ended session no longer stays busy for its peers.** The Claude Code mod and the Codex bridge sent their final idle status without waiting for a busy one still on its way, and peers keep whichever was sealed last. The final idle now waits for it (at most 8 s).
- **Re-friending after `p2p remove` (or `p2p unfriend`) works when the unfriend arrives late.** A copy of the unfriend that reached a device after the new friendship (another device of theirs, or one a relay held back) revoked the caps the new friendship had exchanged, so neither side could message the other. An unfriend now revokes caps only when it ended the last friendship between the two.
- **A message kept in the outbox no longer asks for a receipt.** When the recipient's relays didn't take a message (with this device online), the copy kept to send later still carried the receipt request, and a recipient whose client downgraded meanwhile would reject the whole message. It is now sealed again without one; a copy that already went out on a relay connection whose answer never came is still resent as sealed.
- **The `tui` session's share on a send is taken back only when nothing can have gone out.** A send cut off by the command deadline, or one a relay may have stored without answering, keeps the share, so the reply can still land. And the share is taken back only while the session's roster is still exactly the version it wrote: a change made meanwhile stands.
- **The agent guards no longer let a `p2p send` through on a `--from-session` the CLI won't read as that option.** In the Claude Code mod and the Codex bridge, `p2p send` counted the flag after `--` (where it is message text) or as another option's value (`--to --from-session=x`), and let through a send that went from the `tui` session. Both now read the words as the CLI reads its argv. The shell builds that argv and the guards don't expand it, so they fail closed: a word up to the deciding `--from-session` that isn't written plain (a quote, escape, `$`, backtick, brace, glob, `~` or a redirection) is refused. Put `--from-session` first, written plain. Both guards are pinned to one shared set of test vectors.
- **The Claude Code mod's guard sees more of what can open the terminal UI.** An interpreter reading its program from a pipe, here-string, heredoc or file (`… | node`, `python3 - <<EOF`) on a command that names p2p is refused, as a shell reading one already was, including `/dev/stdin` and `/dev/fd/0` as the script. A text-first command that runs one of its own (`awk` `system()`/`getline`, `sed`'s `e`, `git -c …`, aliases, `bisect run`, `submodule foreach`, `filter-branch`, a rebase exec, `difftool --extcmd`, `rg --pre`) no longer counts as text, and is refused when it mentions p2p. This is still a layer on top of the agent's own permission prompt, not the boundary.

## 0.1.1

Nothing changes on the wire. 0.1.1 and 0.1.0 clients interoperate in both directions. The cross-version matrix ([docs/compatibility.md](docs/compatibility.md)) checks this against v0.1.0 and 70b86c7, as committed at their tags and as npm installs them.

### Upgrade together

- **Update `@peer2peer/cli` and `@peer2peer/ext-ix` together.** The 0.1.1 CLI won't load an `ix` extension unless it declares the graph-target contract (`graphTargets: 1`), and ext-ix 0.1.0 doesn't. With 0.1.1 CLI and 0.1.0 ext-ix, the `ix` namespace is refused with "update @peer2peer/ext-ix". ext-ix 0.1.1's optional peer range on the CLI is `^0.1.1`. Run `npm i -g @peer2peer/cli@0.1.1 @peer2peer/ext-ix@0.1.1`. The Claude Code mod already ships matching copies of both.
- Graph memory needs both at 0.1.1: the 0.1.1 CLI's `p2p watch` drives it and ext-ix 0.1.1 writes it. An older CLI never asks for it.
- Each package depends on exactly `0.1.1` of the others. `@peer2peer/core` has no code changes since 0.1.0.

### Behaviour changes

- **Your own sessions' messages can be held.** In a session that approves its own tool calls (or whose mode is unknown), a message from one of your own **agent** sessions now waits for Deliver, as a peer's does. A peer could otherwise tell one of your agents what to send to another. A message you typed in your own terminal (`p2p tui`, `p2p send`) is still delivered.
  - Messages from **your other devices** are held in such sessions too. Another device can't yet say whether you typed the message or an agent sent it; [RFC #48](https://github.com/ix-infrastructure/Peer2Peer/issues/48) proposes the wire field for that.
  - To turn the hold off, run `p2p own-agents deliver` yourself, in your own terminal; it is refused inside an agent's session. `p2p own-agents deliver --devices <did…>` or `--devices all-other` lets through only your other devices' sessions (agents included), never this device's agents. `p2p own-agents hold` turns the hold back on. The Claude mod and the Codex bridge read the setting when a message arrives, so a change applies at once.
  - Your own sessions are now turn-capped: at most 30 turns per 10 minutes in a session, and at most 10 since you last typed a prompt there. In Codex, your other devices' sessions keep their cap of 5 per 10 minutes. Past a cap, messages are held until you release them: Deliver in the Claude mod, `p2p codex release <id>` in your own terminal for Codex (`p2p codex held` lists them). A sender that asked for receipts gets `held`. Before, the Claude mod didn't cap your own sessions at all.
- **A session goes private when it changes to a folder that can't be placed.** Front ends now read the folders a command moves to: `cd`, `pushd`, `chdir`, `git -C`/`--git-dir`/`--work-tree`, `make -C`, `tar -C`, `ninja -C`, `env -C` and `sudo -D`. Each target is bound as part of the session's projects. A target that can't be resolved, such as `cd -`, `cd $X`, `cd ~other`, `pushd +1` or a bare `pushd`, makes the session private with the reason `unresolved`, and so does an unknown variable at the start of a path. More than 32 such folders in one command makes it private with the reason `folders`. The CLI now gives each cause its own explanation (`projects`, `folders`, `unresolved`, `front`, `constraints`). For a cause that lasts until the session ends, it says to start a new session instead of suggesting you share the project.
- **`p2p ix import` and `p2p ix note --ix-note` use only the open-source `ix note`, against your local graph.** In 0.1.0 they ran whatever `ix note` answered, which was Ix Pro's: it reads and writes your Ix cloud org.
  - They now run only when the `ix` that answers has the open-source `ix note` and `ix session` (Ix after 0.13.0, without Ix Pro), which `ix --help` shows. With Ix Pro installed, or with an older Ix, they are refused with `graph_target` before anything is read or written, and the message says which (with an older Ix, upgrade).
  - Every graph target is local until shared graph memory lands. Against a shared target, every `ix note` and `ix session` call is refused.
  - Against a local target, ext-ix runs `--help`, `--version`, `impact`, `around`, `overview`, `inventory`, `context`, `subsystems` and `status`, and only its own exact forms of `ix note` and `ix session`: show a note by id or a session by name or id, write a note with its text on stdin, and create a `p2p-<session id>` session record. Any other form is refused with `graph_target`.
  - Before either command, the local endpoint's port must be held by your own process (see graph memory below), or it fails with `ix_listener`. A write whose stderr doesn't confirm it went to the local endpoint fails with `ix_unconfirmed`.
  - `p2p ix import` still needs your consent for exactly the note shown. The note is written with a first line `Shared by <address> over Peer2Peer`.
  - `--ix-note` refuses a graph-memory record of another session unless that session's context may go where this one's does: both sessions in shared projects, everyone the sending session reaches also reached by the recorded one, and the same graph target. A record whose session can't be told is refused too.
  - Plain `p2p ix note` messages to peers (`x:ix.note`) are unaffected.
- **`ix` runs with a pinned endpoint and a minimal environment.** ext-ix takes Ix's endpoint only from p2p's graph target, which is the loopback `ixEndpoint` in `config.json` or the default `http://localhost:8090`, never `IX_ENDPOINT` from the environment. It runs `ix` with an allowlisted environment, so the caller's `IX_ENDPOINT`, `IX_PAT`, `IX_ORG`, `P2P_*`, `NODE_OPTIONS` and proxy settings don't reach it, and background map refresh and update checks are off.
- **A same-device send to yourself is refused with `self_send`.** Before, `--to <you>/<own sid>` was `not_found`.

### New

- **`p2p history`**: messages this device sent and received, kept only on this device. They're encrypted at rest with ChaCha20-Poly1305 under a key of their own (`cli/history.key`, 0600), kept for 30 days up to 8 MiB by default, and sent to no relay or peer. The key is stored next to the data in your home folder, so the encryption protects copies of the history files (backups, sync), not against anyone who can read your account.
  - Options: `--session <sid>` or `--inbox`, `--peer`, `--circle`, `--since 30m|12h|7d|<date>`, `--limit`, `--clear` and `--json`.
  - The full history and the inbox belong to the person: they need the front end's token or your `yes` on the terminal, and are refused inside an agent's session. A session sees only its own history.
  - Settings: `history.enabled`, `history.retentionDays` and `history.maxBytes` in `config.json`. `P2P_HISTORY=0` stops recording.
  - The TUI's Messages screen merges in the history (`h` toggles the inbox only). The Codex bridge has a `p2p_history` tool, and the Claude mod has `/peers history [inbox|here]` and `/peers inbox`.
- **Send to another session on the same device.** `p2p send --to "<you> [ref]"` or `--to <you>/<sid>`, the mod's `SendMessage` and the bridge's `p2p_send` now reach another session of yours on this device when it is named. A bare `--to <you>` still means your other devices. The message goes through your relay sealed to this device, under the same rules as your other devices. Delivery receipts and `--notify-when-idle` work for these sends.
- **Shares that cover subfolders: `p2p project share --subfolders`** (and `/peers project share --subfolders`). A shared non-git folder can cover the folders below it.
  - Coverage is opt-in, so existing shares stay exact.
  - A covered subfolder never crosses a git repository (bare ones included) or a `.p2p-private` marker while its `.git` or marker is there, nor a folder with its own policy.
  - `--subfolders` is refused for `/`, your home folder and the folders above it, the temp folders and the system's top folders, and ignored with a warning on a git repository.
  - At share time it warns about nested repositories and `.p2p-private` folders.
- **`p2p session show <sid>`** (and `/peers session`, typed only): a session's bound projects, who it reaches, every reason it is private, and what to do. It is refused inside an agent's session without the front end's token.
- **Graph memory: your sessions in your local Ix graph** ([#53](https://github.com/ix-infrastructure/Peer2Peer/pull/53), [docs/concepts.md](docs/concepts.md)). With the `ix` extension enabled and an Ix that has the open-source `ix note` (Ix after 0.13.0, without Ix Pro), `p2p watch` records this device's own sessions into your local Ix graph as they run. The Claude mod runs `p2p watch` for each session, so it records them too.
  - **Only sessions in shared projects.** A session whose project ceiling isn't shared (a private or unmapped project, `.p2p-private`, not bound yet) is never recorded, and one that becomes private stops being recorded. Peers' statuses and your other devices' sessions are never recorded.
  - **What it writes**, through the open-source `ix note` and `ix session`: an Ix session record `p2p-<session id>` with the session's label, repository and branch, and a note for its start, each new status line, the repo-relative files it edits, and its end. Every note is tagged `finding` and starts with "Recorded by Peer2Peer (agent-generated, untrusted)". File names with whitespace or control characters, or longer than 200 characters, are left out. Message bodies are never written, and a note a peer shares goes in only when you import it with `p2p ix import`.
  - **Off the hook path, best effort.** `p2p status` runs no Ix. `p2p watch` reads the statuses the session already posted every 5 seconds and queues what changed; at most 64 items wait, and past that new items are dropped. A session's end is written by the next `p2p watch` running on this device. Every dropped item is counted by reason in `p2p doctor`.
  - **Local only.** Each batch must have a local graph target, or it is dropped as `not_local` and never handed to ext-ix, and ext-ix checks the target again. Each write must print on stderr that it went to the local endpoint, or it is skipped as `ix_unconfirmed` and writing stops. With Ix Pro installed (its `ix note` writes to your cloud org) or an older Ix, nothing is written and the doctor says why.
  - **Only to your own backend.** Before writing, ext-ix checks that every listener on the local endpoint's loopback or wildcard port is your own process (Linux: `/proc/net/tcp`; macOS: `netstat` and `lsof`; on other platforms the check can't tell, so nothing is written). A root-owned listener is refused unless you set `"ixTrustRootListener": true` in config.json by hand: Docker's port proxy on Linux runs as root, so set it only if that Docker is yours alone. Otherwise nothing is written (`ix_listener`) and the doctor says what to do. On a machine other people log in to, turn graph memory off.
  - **Turning it off:** `"ixMemory": false` in config.json, or `P2P_IX_MEMORY=0`. The environment can only turn it off.
  - Ix's `-` shorthand (the last note or session shown or created) may name a Peer2Peer record after a background write, instead of your own last note.
- **Ix is on by default, and `p2p doctor` has an Ix section.**
  - `p2p setup` on a new install enables the `ix` extension when both the Ix CLI and `@peer2peer/ext-ix` are found, and otherwise says how to get them. Setup installs nothing. Only you can enable it: with the front end's token or your `yes` on the terminal, never from inside an agent's session.
  - An existing install never changes silently. It gets a one-time notice at a terminal instead.
  - The doctor's Ix section shows the Ix binary and version, whether the extension is enabled, the local backend's health, whether the project here is mapped, and each project's graph target. With Ix installed and the extension on, it also shows whether graph memory is on or off and why, how many items were written and queued, how many were dropped and why, why writing last stopped, and whether `ixTrustRootListener` is set. None of these is a failure. Without Ix, nothing in that section is a failure.
  - `p2p project show|ls` print each project's graph target (`graph: local only (http://localhost:8090)`).

### Fixes

- Project boundaries bind less noise, so sessions go private by mistake less often:
  - `/dev/null` and other device or pseudo files are no longer projects.
  - The scripts of `sed`, `jq`, `awk`, `perl -e`, `python -c`, `sh -c` and similar commands are no longer read as paths, while the absolute and relative paths written inside them now bind.
  - `$HOME`, `$PWD` and `$CLAUDE_JOB_DIR` are expanded when the front end knows their real value.
  - Paths are sent as written, so `git -C /src/secret.repo` binds `/src/secret.repo`, not `/src`.
- Every check stays fail-closed, and each case found in the [#45](https://github.com/ix-infrastructure/Peer2Peer/issues/45) review is closed and tested ([#49](https://github.com/ix-infrastructure/Peer2Peer/pull/49)); remaining gaps are tracked in [#51](https://github.com/ix-infrastructure/Peer2Peer/issues/51).

### Release process

- The cross-version matrix runs on every pull request and in the release workflow, against the previous two release tags from git and from npm ([#36](https://github.com/ix-infrastructure/Peer2Peer/pull/36)).
- The relay install scripts are pinned to the v0.1.0 source tarball ([#39](https://github.com/ix-infrastructure/Peer2Peer/pull/39)). They move to v0.1.1 in a follow-up after this release, once its `SHA256SUMS` exists.

## 0.1.0

The first npm release. These notes were added after it shipped, because the release itself carried only the generated text.

- **Invite codes and `p2p remove`.** A code records which circles its redemption actually put the redeemer in, and `p2p remove` takes the redeemer out of only those, never out of a circle they were already in. Codes redeemed before invite links shipped have no such record. For them, `p2p remove` falls back to undoing every circle the code named.
- **Invite codes on private relays.** A code or link whose relay host is, or resolves to, a loopback, link-local or private address is refused unless the redeemer passes `p2p join --allow-private-relay` (or sets `P2P_ALLOW_PRIVATE_RELAY=1`).
  - The same applies to a code whose inviter's relays are such relays, to pasted long invite links (`p2p accept`) and to circle links (`p2p circle join`) that name one.
  - Held invites and rotations from friends on such relays are approved as before. A relay that is already one of yours (a team's Tailscale or LAN relay) never needs the flag.
  - In Claude Code: `/peers join --allow-private-relay <code>`.
